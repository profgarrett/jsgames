# Plan: Running a Prolific Study on the jsgames Platform

**Scope of this document:** maps the requested study (Prolific recruitment → identification → pre-survey → task with video + AI chatbot + agreement reflection → post-survey) onto jsgames' existing Level/Page architecture. Decisions are now resolved (§ "Decisions (resolved)" below): **2 conditions**, a **live ChatGPT (OpenAI) chatbot** with **full transcript logging**, an **externally hosted video**, and a **completion code** shown on the final page. A `testprolificstudy` level with sample content has been implemented to validate the approach, the **Prolific PID capture / auto-login flow is implemented**, and **results extraction (survey answers + chat transcripts) now works through the existing reporting UI** (see the repo).

## 1. How the study maps onto existing concepts

jsgames already has the right shape for this. A **Level** (`IfLevelSchema`) is a numbered sequence of **Pages**, saved as one JSON blob per participant-attempt, exactly like a survey instrument with branching sections. The whole study — consent, pre-survey, video, chat, reflection, post-survey, completion code — becomes **one Level**, built the same way existing tutorials are built: composing reusable page snippets (like `consent.ts`, `numeracy.ts`, `feedback.ts`, `finish_questions.ts`) with `LinearGen`/`ShuffleGen` in `Gens.ts`.

A **Section** (join-code based) becomes the **study container**: one join code identifies "this Prolific study," and section membership is already how jsgames groups users for reporting (`app_reports.ts` filters by `idsection`). If a second study or a pilot is needed later, a second section/join code separates the data cleanly with zero new code.

| Study element | Existing jsgames mechanism | Reuse as-is? |
|---|---|---|
| Consent screen | `src/server/pages/consent.ts` (`IfPageTextSchema`) | Yes |
| Pre-/post-survey questions (multiple choice, Likert-style, free text) | `IfPageChoiceSchema`, `IfPageShortTextAnswerSchema`, `IfPageLongTextAnswerSchema` | Yes |
| "Agreement with the AI" reflection | `IfPageChoiceSchema` with `client_items` like `['Strongly agree' … 'Strongly disagree']` (same pattern already used for comfort-level questions) | Yes |
| Video | Ad-hoc `<iframe>` embed inside a page's `description`, as already done in several `kcs/*.ts` files | Yes, pattern exists |
| Study grouping / data isolation | Sections + join codes | Yes |
| Per-participant timing | `app_pageviews.ts` (load + 30s heartbeats, server-clamped) | Yes |
| Data export for analysis | `app_reports.ts` → `iflevels` rows rehydrated into per-page answers | Yes, with one addition (§5) |
| **AI chatbox embedded in the task** | Nothing exists | **New — the core build item** |
| Condition assignment (2 arms) | The `versions` page-template mechanism (`IfLevelSchemaFactory._initialize_json`, seeded by `level.seed`), already used by several tutorials to vary content per attempt | Yes, direct reuse |
| **Prolific ID capture / identification** | New `/prolific` landing route + `POST /api/users/prolific_login` | **New — implemented** |
| **Content authoring UI** | None — all levels are hand-written TypeScript | Not needed for a one-off study; author it as code like every other level |

## 2. Participant flow

1. Participant clicks the Prolific study link, which points at the app's `/prolific` route and carries `?PROLIFIC_PID=...&STUDY_ID=...&SESSION_ID=...` (Prolific's standard auto-appended params) plus two researcher-configured query params, `level=<level code>` and `section=<join code>` — e.g. `https://excel.fun/prolific?level=testprolificstudy&section=<join code>`.
2. The new `ProlificRouter` landing page (`src/app/if/ProlificRouter.tsx`) reads all five params and calls the new `POST /api/users/prolific_login` route (`src/server/app_users.ts`), which auto-provisions (or logs into) an account keyed to `PROLIFIC_PID` as the username — the same find-or-create-then-`user_login()` pattern already used for Google login, adapted to not require a Google credential — and joins the given section automatically (`auth_provider = 'prolific'`).
3. `ProlificRouter` then checks (via the existing `GET /levels/byCode/:code` route) whether this participant already has an in-progress attempt at the level and resumes it if so; otherwise it creates a new one via `POST /new_level_by_code/:code`, now optionally stamped with `prolific_study_id`/`prolific_session_id` in the level's history for traceability. The participant is deep-linked straight into the study Level (skipping the normal dashboard).
4. Level plays page-by-page: consent → pre-task survey pages → condition-dependent task (video + chat) → agreement/reflection question(s) → post-task survey pages → a final page showing the Prolific completion code (or redirecting to Prolific's completion URL).
5. Participant returns to Prolific and submits.

## 3. Condition assignment (2 arms) — implemented via the `versions` mechanism

jsgames already has a built-in way to give one page template multiple random variants: a page can carry a `versions: [...]` array, and `IfLevelSchemaFactory._initialize_json` picks one entry using `DataFactory.randomizeList(versions, level.seed)`, where `level.seed` is a random number assigned once per participant when their level is created. This is the exact mechanism several existing tutorials (e.g. `if1.ts`) already use to vary a formula question's wording/solution per attempt — it turned out to be a perfect, zero-new-code fit for condition assignment too.

The chat page in `testprolificstudy.ts` uses `versions: [ { solution_system_prompt: agreePrompt, tags: [...] }, { solution_system_prompt: skepticalPrompt, tags: [...] } ]`. Since this page sits at a fixed position in the level, the version picked reduces to a seed-shuffled, per-participant 50/50 choice — confirmed by an offline test run (§8) that split 4 simulated participants 2/2 across the two conditions. No changes to `misc.ts`'s `random_boolean_from_string` (or anything else) were needed.

The assigned condition is stored as a `tag` on the chat page itself (`condition_agree` / `condition_skeptical`), so analysis doesn't need to re-derive it, and condition balance can be eyeballed directly in the stored data.

## 4. The new build: an AI chatbox page

This is the one genuinely new feature. It has three pieces, all small and self-contained:

- **A new page type** (alongside `IfPageChoiceSchema`, `IfPageLongTextAnswerSchema`, etc.) that renders a simple message list + text input, and stores the full transcript as its "answer" — structurally the same as how a long-text answer page stores one string, just storing an array of turns instead.
- **One new server route** that proxies chat turns to an LLM API (e.g., Claude or OpenAI) with a system prompt that encodes the condition (e.g., an AI that affirms the participant's stated view vs. one that pushes back). This mirrors the existing pattern of a small, focused Express route file (`app_users.ts`, `app_sections.ts`, etc.) rather than anything architecturally new.
- **Guardrails**: a per-page cap on number of turns and/or a max-tokens ceiling, both to bound API cost across however many Prolific participants are recruited and to keep the conversation within the scope the study needs. Given the "live LLM" choice, a fixed, condition-specific system prompt (rather than free-form persona instructions from the page config) is the simplest way to keep the manipulation consistent and auditable for IRB purposes.

The **video page** needs no new page type: reuse `IfPageTextSchema` with an embedded `<iframe>` pointing at the unlisted YouTube/Vimeo link, exactly like the existing SQL tutorial pages already do. If it's worth the small cleanup, a dedicated `video_url` field could be added to the base page schema so it's not raw HTML — but that's optional polish, not a requirement.

## 5. Data collection and export

Everything funnels into the existing `iflevels` table and `app_reports.ts` pipeline: survey answers, the agreement/Likert response, and the chat transcript all live inside the Level's `pages` JSON, keyed by username/section/level code, and come back out through the same admin reporting routes used for coursework today. This is now fully wired up (see §8 item 5): `GET /api/reports/answers` returns one flat row per page per participant — across every page type this study uses (formula, choice, number, short/long text, chat, and static text/consent) — and the `/ifgame/questions/:idsection` admin page's "Excel" output (copy-paste into a spreadsheet) now renders that data directly, no manual JSON wrangling required. Page-view timing (`app_pageviews.ts`) gives time-on-video and time-in-chat "for free."

For quick reading rather than bulk export, `/ifgame/recent/:idsection` already rendered every page type generically (including full chat transcripts) before this change and needed nothing further — good for spot-checking a handful of participants.

| Item | Size | Why needed |
|---|---|---|
| Prolific PID capture + auto-login | Small | No URL-param identification flow existed — **implemented** (`/prolific` route, `ProlificRouter.tsx`, `POST /api/users/prolific_login`) |
| Condition assignment (2 arms) | None | Direct reuse of the existing `versions` page-template mechanism |
| Chat page type (render + store full transcript) | Medium | Nothing like it exists — **implemented** |
| Chat proxy server route (OpenAI Chat Completions call, system prompt per condition, turn/token caps) | Medium | Nothing like it exists — **implemented** |
| Completion-code / redirect-to-Prolific page | Small | Reuses `IfPageTextSchema`, just new content |
| Chat transcript (+ survey answers) included in reporting export | Small | Extends existing export function and its Excel UI — **implemented** |
| Study Level itself (consent + survey pages + video page + chat page + reflection + survey pages), composed from existing page snippets | Content authoring, not new infrastructure | — |

Everything else — consent, surveys, Likert-style agreement question, video embed, section-based cohorting, per-page timing, data export — is pure reuse of what's already in the codebase.

## 7. Non-functional considerations to plan for

- **IRB / consent**: extend the existing `consent.ts` template rather than writing new consent language from scratch; explicitly disclose that participants will converse with an AI, since that's a material fact for consent.
- **Cost and abuse control**: cap chat turns per participant and set a hard max-tokens budget per call (both done — see §9); consider a per-account or per-IP rate limit on the new chat route since it's the one endpoint that costs money per call (done at the account-creation and attempt-creation layers instead — see §9).
- **Attention/quality checks**: jsgames doesn't currently have a bot-check/attention-check question type; a plain multiple-choice "attention check" page (reusing `IfPageChoiceSchema`) is easy to insert into the survey blocks and is worth including given Prolific samples.
- **Payment/completion**: decide up front whether to use Prolific's completion-URL redirect or a completion code shown on the final page — both are trivial with `IfPageTextSchema`, but the choice affects the very last page's content.
- **Pilot before full launch**: run 5–10 real Prolific participants first to check timing (for setting a fair Prolific reward), chat log quality per condition, condition balance, and that the completion step actually returns people to Prolific correctly.

2. ~~Condition assignment~~ — **done, via reuse.** No new randomization code was needed: the chat page's `versions` array (the same mechanism already used elsewhere in this codebase to vary page content) picks one of the two system prompts per participant, seeded by the level's existing random `seed`.
3. ~~Assemble a study Level from existing + new page snippets~~ — **done as `testprolificstudy`** (src/server/tutorials/testprolificstudy.ts): consent → 2 pre-survey pages → video → AI chat → agreement reflection → 2 post-survey pages → completion code. Registered and playable at `/ifgame/levels/testprolificstudy` once logged in.
4. ~~Prolific PID capture + auto-login/account provisioning~~ — **done.** New `/prolific` landing route (`src/app/if/ProlificRouter.tsx`, registered in `src/app/index.jsx`) reads `PROLIFIC_PID`/`STUDY_ID`/`SESSION_ID` plus researcher-set `level`/`section` params, calls the new `POST /api/users/prolific_login` (`src/server/app_users.ts`, modeled directly on the existing `google_login` route) to find-or-create the account and join the section, then resumes an in-progress level or starts a new one (now optionally stamped with `prolific_study_id`/`prolific_session_id` via an extension to `POST /new_level_by_code/:code` in `src/server/app_levels.ts`).
5. ~~Chat transcript (+ survey answers) included in reporting export~~ — **done, including static/number pages.** `build_answers_from_level` (`src/shared/IfPageSchemas.ts`) now emits a row per page for every page type this study uses — `IfPageChoiceSchema`, `IfPageShortTextAnswerSchema`, `IfPageLongTextAnswerSchema`, `IfPageChatSchema`, `IfPageNumberAnswerSchema`, and `IfPageTextSchema` (consent/video/completion-code) — not just `IfPageFormulaSchema`, tagged with a new `page_type` field. `IfPageTextSchema` reports whether the page was actually reached (`'read'`/`'not read'`, using `client_has_answered()`) rather than its `toString()`, which always returns the literal string `'read'` regardless of state. Two bugs in the existing report pipeline that would otherwise have silently hidden this study's data were also fixed: `GET /api/reports/answers` (`app_reports.ts`) required `users.username LIKE '%@%'`, which excluded every Prolific account (`prolific_<pid>`, no `@`) — removed; and `GET /api/reports/questions` treated an empty/`'All'` pagetype as "match nothing" instead of "match everything" — fixed so a level mixing several page types can be pulled in one call. On the client, `QuestionsData.tsx` gained summary branches for short/long text, chat, and static-text pages (Number was already handled), `QuestionsExcelChoice.tsx` was widened from Choice-only to flatten all six of those types into its copy-to-Excel table (with a new `a_type` column), `Filter.tsx`'s page-type dropdown now lists Chat/Short text/Long text/Text-consent, and `Questions.tsx` now auto-picks the Formula exporter or the (widened) Choice/survey exporter based on which page types are actually loaded — so the existing "Excel" output button on `/ifgame/questions/:idsection` works end-to-end for this study with no new UI. Verified offline (see below) that all 9 pages of a completed `testprolificstudy` level now produce an export row; not yet exercised against a live server.
6. Pilot with a small Prolific batch, check data end-to-end, then launch fully — plus reviewing the sample consent text, video, survey wording, and system prompts in `testprolificstudy.ts` (all currently marked `[SAMPLE ... ]` placeholders), and adding a real `OPENAI_API_KEY`.

### How to try the test level

**Via normal login** (as before):
1. Add a real key to `OPENAI_API_KEY` in `src/server/secret.js` (a blank key makes the chat route return a clear "not configured" error instead of a raw failure).
2. Start the dev server (`npm run startnode` and `npm run startreact`, in two terminals) and log in.
3. Visit `/ifgame/levels/testprolificstudy`, start the level, and play through it — including a couple of chat exchanges — to see the AI reply and the condition-specific behavior (the two conditions are an agreeable vs. a mildly skeptical AI persona; which one you get is randomized per attempt).

**Via a simulated Prolific link** (new): with the dev server running, visit `http://localhost:8080/prolific?PROLIFIC_PID=test123&STUDY_ID=abc&SESSION_ID=xyz&level=testprolificstudy&section=<a real join code>` while logged out. This should auto-create/log into a `test123`-keyed account, join the given section, and drop straight into the level — no manual login form. Reloading the same link mid-attempt should resume rather than restart. This step still needs a real Prolific ID/username to be free of collisions with any account already created from a prior test run; a different `PROLIFIC_PID` value avoids that.

## 9. Abuse hardening — untrusted chat/study participants

The Prolific flow deliberately lets an unverified stranger provision their own account and drive a real, cost-incurring AI feature, so this got a dedicated security pass. What's already solid, unchanged: `max_turns` is checked against the DB-stored count (not anything the client can claim), `client_messages` can't be written through the generic level-update route (only the dedicated `/chat` route can touch it), messages are capped at 4000 characters, completions capped at 300 tokens, and the chat page's `solution_system_prompt` never reaches the client (`_strip_secrets` drops it correctly). Two problems were found and fixed:

- **Stored XSS via chat transcripts (and other free-text answers) in the admin reporting UI.** `QuestionsData.tsx` built `summary_answer.html` directly from participant-controlled text (`page.client_messages[].text` for chat; `page.client` for choice/short/long-text answers), and `QuestionsTable.tsx`'s `Expandable` renders that `.html` field via `dangerouslySetInnerHTML`. A participant could type something like `<img src=x onerror="...">` in the chat box and have it execute in a faculty/RA's authenticated browser the moment they expanded that answer in the Table view — a real path to session-cookie theft. **Fixed**: those `.html` assignments now run through `he.encode()` (the same escaping the Formula/SQL branches already used), for Choice, Short/Long text, and Chat. Verified offline: a level with an `<img onerror=...>` payload planted in chat, choice, and short-text answers now produces `.html` values with zero raw `<`/`>` characters — the payload renders as inert text, not markup. (Also found and fixed, while testing this: `create_summary_question` crashed with a null-pointer error on any `IfPageNumberAnswerSchema` used as a plain survey question with no fixed solution — exactly `testprolificstudy`'s pattern — which would have broken the whole Questions page for this study; now guarded.)

- **Unbounded cost/DoS via self-service account and attempt creation.** `POST /api/users/prolific_login` accepts any string matching the ID charset with no verification against a real Prolific session, and `POST /new_level_by_code/:code` had no cap on how many attempts one account could start — so a script could mint unlimited accounts and unlimited chat-page attempts, each with its own turn budget, with nothing to stop it (no rate-limiting existed anywhere in the app). **Fixed**: added a small dependency-free in-memory rate limiter (`src/server/rate_limit.ts`, fixed-window, keyed by IP) and applied it to both routes — `prolific_login` allows 20 calls per IP per 10 minutes, `new_level_by_code` allows 60 per IP per 15 minutes. On top of that, `new_level_by_code` now caps total attempts of the same level code at 3 per username, **scoped only to `prolific_`-prefixed usernames** (a deliberate choice — a blanket cap would risk breaking normal students/faculty who legitimately retry a tutorial many times for practice; Prolific accounts are the actual threat surface, and `ProlificRouter.tsx`'s resume-in-progress logic means a real participant should rarely need more than one or two attempts anyway). Verified the rate limiter's window/reset/per-key-isolation logic offline, and confirmed both edited route files still load without syntax errors.

Not implemented, and worth a conscious decision before a real study: no content-moderation check runs on the participant's message or the AI's reply before it's generated and permanently logged, so a hostile participant could still attempt to jailbreak the persona into producing something you wouldn't want attributed to the study or your OpenAI account (it just can no longer execute as HTML in your browser when you review it). Adding an OpenAI moderation-endpoint call before/after the chat completion would close this if it matters for this study's risk profile. The rate-limit numbers above (20/10min, 60/15min, 3 attempts/username) are this session's judgment call, not something you specified — adjust them if they're wrong for your expected participant volume.

## Decisions (resolved)

- **Conditions**: 2 arms, implemented via jsgames' existing `versions` page-template mechanism (seeded per-participant by `level.seed`) rather than any new randomization code — see §3.
- **LLM backend**: ChatGPT (OpenAI Chat Completions API). The new chat server route calls OpenAI directly with a condition-specific system prompt; requires an `OPENAI_API_KEY` added to `secret.js`/`secret.distribution.js` alongside the other secrets.
- **Transcript logging**: every AI response and every participant message is logged, in order, as part of the chat page's stored answer (role, text, timestamp) — nothing is summarized or dropped, matching how other page types store a full history.
- **Completion**: the final page of the level displays a completion code in plain text for the participant to copy and paste back into Prolific (not an automatic redirect to Prolific's completion URL).
- **Prolific PID capture / auto-login**: implemented as a `/prolific` landing route + `POST /api/users/prolific_login` (find-or-create account keyed to `PROLIFIC_PID`, `auth_provider = 'prolific'`, auto section-join, auto-login, resume-in-progress-level check) — see §2 and §8 item 4.
- **Results extraction**: use the existing reporting UI — `GET /api/reports/answers` for a flat, all-page-types spreadsheet-ready export (now including survey and chat rows), or `/ifgame/questions/:idsection` → Excel output for a one-click copy-to-Excel table; `/ifgame/recent/:idsection` for a quick read-through of individual transcripts. See §5 and §8 item 5.
- **Abuse hardening**: chat/survey answers are now HTML-escaped before being rendered in the admin reporting UI (closing a stored-XSS path), and `/prolific_login` + `/new_level_by_code` are rate-limited and attempt-capped for Prolific accounts specifically. See §9.

## Open decisions still worth pinning down

- Exact wording of the pre-/post-survey instruments (can be dropped into the existing page-snippet pattern once finalized).
- Target sample size per condition and Prolific screening criteria (affects nothing architecturally, but affects the reward/timing pilot).
- Actual wording/strength of the two chatbot system prompts (the manipulation itself) — sample/placeholder prompts are used in the test level and should be reviewed before a real study.
- The Prolific auto-login flow, the reporting-export changes, and the abuse-hardening changes have not been live-tested against a running dev server/MySQL or in an actual browser (none was reachable in this session) — worth a manual click-through (including opening `/ifgame/questions/:idsection`, selecting the study, checking the Excel output, and confirming a 429 actually shows a sane message to the client) before piloting with real participants.
- No content-moderation check on chat messages/replies (§9) — worth adding if this study's risk profile calls for it.
- The rate-limit and attempt-cap thresholds (§9) are a starting guess, not tuned to this study's actual expected participant volume — revisit before a real launch.
